# 실시간 체결 알림 서비스: 전체 처리 시나리오와 대응 설계

작성 기준: 현재 저장소의 구현과 설정

## 1. 문서 목적

이 문서는 토스증권 OpenAPI에서 체결 데이터를 받은 순간부터 목표 가격 조건을 판별하기까지의 전체 흐름을 정리한다. 각 단계가 언제 실행되는지, 예상되는 문제가 생기면 현재 어떻게 동작하는지, 아직 결정하거나 구현해야 하는 대응이 무엇인지 한눈에 파악하는 것이 목적이다.

대규모 운영 부하를 측정한 결과 문서가 아니다. 모든 부하를 사전에 재현할 수 없으므로, 서비스에서 발생할 상황을 가정하고 선택한 설계와 그 한계를 명시한다.

## 2. 현재 범위와 중요한 전제

- 국내와 미국 시장의 웹소켓 연결을 앱 시작 시 요청한다. 인증 정보가 없으면 연결을 건너뛴다.
- 수신 체결을 시장과 종목별로 메모리에서 집계한다.
- 시간 제한 또는 건수 제한에 도달하면 가격 범위 이벤트를 Kafka에 발행한다.
- Kafka Consumer는 이벤트를 받아 DB의 활성 목표가격 알림을 판별하고, 처음 조건을 충족한 알림을 `FIRED`로 바꾼다.
- 실제 푸시·이메일 등 사용자 알림 발송은 현재 범위가 아니다.
- 웹소켓 재연결, 집계 중 데이터의 디스크 보존, Kafka 발행 재시도·실패 복구, Consumer 재시도·DLQ는 아직 구현되어 있지 않다.
- 따라서 현 구현은 목표가격 판별 흐름을 연결한 초기 버전이다. 장애 복구까지 보장하는 운영 설계로 간주하지 않는다.

## 3. 전체 그림

```text
앱 시작
  └─ 인증 정보와 종목 설정 확인
      └─ 토큰 발급 → 국내/미국 WebSocket 연결 및 구독 요청
          └─ 구독 응답 확인 → 체결 메시지 수신
              └─ 시장·종목별 메모리 배치에 가격 반영
                  ├─ 최대 500건 도달: 즉시 배치 마감
                  └─ 배치 시작 후 100ms 경과: 예약 작업이 배치 마감
                      └─ minPrice/maxPrice 이벤트 생성
                          └─ Kafka 토픽에 비동기 발행, 라운드로빈으로 파티션 선택
                              └─ Consumer가 JSON을 이벤트 객체로 변환
                                  └─ DB에서 해당 종목·가격대의 ACTIVE 알림 조회
                                      └─ 조건부 상태 변경 ACTIVE → FIRED
                                          └─ 처음 변경에 성공한 알림을 로그로 확인
```

## 4. 단계별 시나리오

### 4.1 앱 시작과 시세 연결

앱 시작 시 `TossInvestWebSocketRunner`가 인증 정보와 구독 종목을 확인한다. 인증 정보가 모두 비어 있으면 외부 연결 없이 앱을 실행한다. 한쪽 값만 있거나 종목 목록이 비어 있으면 시작 오류가 발생한다. 설정이 유효하면 토큰을 발급받고 국내와 미국 시장별 연결을 연 뒤 구독 요청을 보낸다.

웹소켓 연결 성공 로그는 서버와의 연결이 맺어졌다는 뜻이다. 별도의 구독 응답에서 승인·거절 종목을 확인해야 구독 요청 결과를 알 수 있다. 승인된 종목이라도 거래가 없으면 체결 메시지는 오지 않는다.

**예상 상황과 현재 대응**

- 인증 또는 연결 실패: 연결 단계에서 오류 로그 또는 앱 시작 오류로 드러난다. 자동 재연결은 없다.
- 구독 일부 거절: 승인 수와 거절 목록을 로그로 확인한다. 거절 종목을 자동으로 재요청하지 않는다.
- 연결 이후 단절: 현재 재연결하지 않는다. 운영 적용 전 연결 상태 감시와 재구독 절차가 필요하다.

### 4.2 체결 수신과 종목별 배치

웹소켓의 완성된 JSON 메시지에서 시장, 종목 코드, 체결 가격을 추출해 `TradeExecutionBatchAggregator.accept`에 전달한다. 배치 키는 시장과 종목 코드의 조합이다. 따라서 국내 `005930`과 미국 시장의 같은 문자열 코드는 별도 배치다.

첫 체결이 들어오면 해당 종목의 배치가 만들어지고 시작 시각을 기록한다. 이후 가격마다 최저가, 최고가, 체결 수를 갱신한다. 배치 종료 조건은 둘 중 먼저 발생한 것이다.

1. 배치에 포함된 체결이 500건에 도달한다.
2. 첫 체결부터 100ms가 지난다. 예약 작업은 10ms 간격으로 만료된 배치를 확인하므로 실제 마감은 스케줄 지연과 처리 지연만큼 100ms보다 늦을 수 있다.

체결이 계속 들어오면 `accept`도 만료 여부를 확인한다. 이미 100ms가 지난 배치는 새 체결을 넣기 전에 먼저 마감하고 새 배치를 시작한다. 체결이 더 오지 않아도 예약 작업이 배치를 마감한다.

예를 들어 한 배치에 `100, 104, 98, 102` 가격이 들어오면 Kafka 이벤트에는 개별 순서 대신 `minPrice=98`, `maxPrice=104`, 체결 수 4와 배치 시각 범위가 담긴다.

**이 선택이 해결하려는 문제와 비용**

- 모든 체결을 Kafka에 각각 보내는 대신 배치당 한 이벤트를 보내 Kafka 메시지 수와 Consumer의 조건 조회 횟수를 줄인다.
- 배치가 길수록 이벤트 수는 감소하지만 알림 판정이 늦어진다. 100ms와 500건은 현재 설정값이며 부하 측정으로 검증된 최적값은 아니다.
- 최저·최고가만 남기므로 개별 체결 순서와 최초 목표가 도달 시각은 알 수 없다. 이 서비스가 가격 도달 여부를 판정하는 범위에 맞춘 손실이다.
- 배치는 프로세스 메모리에만 있다. 앱이 배치 마감 전에 종료되면 그 배치의 체결 데이터는 복구되지 않는다.
- 여러 종목의 배치 자료구조 변경이 하나의 동기화 잠금을 공유한다. 종목이 많거나 콜백이 밀릴 때 병목이 되는지 추후 계측해야 한다.

### 4.3 이벤트 발행과 Kafka 저장

배치가 마감되면 `TradeExecutionEvent`를 만들고 JSON 문자열로 변환해 `defomo.trade-executions` 토픽에 비동기 발행한다. 메시지 키와 파티션 번호를 지정하지 않으므로 Producer의 `RoundRobinPartitioner`가 파티션을 고른다. 현재 토픽 설정은 파티션 6개, 보관 기간 7일이다.

Kafka는 이벤트를 선택된 토픽 파티션의 로그에 기록한다. 발행 완료 로그의 파티션과 offset은 어느 파티션의 어느 위치에 기록됐는지 추적하는 데 쓸 수 있다. 로컬 Compose는 Kafka 브로커 한 개와 복제 계수 1로 실행되므로, `acks=all` 설정만으로 브로커 장애에 대한 복제 내구성이 생기지는 않는다.

**예상 상황과 현재 대응**

- JSON 변환 실패: 발행 전에 오류 로그를 남긴다. 해당 배치는 자동 재시도하지 않는다.
- Kafka 발행 실패: 비동기 완료 콜백에서 오류 로그를 남긴다. 이벤트를 별도 저장하거나 재발행하지 않는다.
- 같은 종목 이벤트의 순서: 라운드로빈은 같은 종목도 서로 다른 파티션으로 보낼 수 있다. 따라서 종목 전체의 순서는 보장하지 않는다. 현재 알림 판정은 배치의 min/max 범위를 사용하므로 순서보다 분산을 선택했다.
- Kafka가 소비되지 않는 동안: 설정된 보관 기간 동안 이벤트가 토픽에 남을 수 있다. 보관 기간이 지난 데이터는 삭제 정책에 따라 만료되며, 장기 보관 기록으로 취급하지 않는다.

### 4.4 Consumer 수신과 알림 조건 판별

`TradeExecutionEventKafkaConsumer`는 전용 Consumer 그룹으로 토픽을 읽는다. 레코드 값인 JSON 문자열을 `TradeExecutionEvent`로 변환하고 `AlertConditionEvaluationService`에 전달한다.

서비스는 시장과 종목이 같고 상태가 `ACTIVE`인 알림 중 가격 범위에 조건이 포함되는 알림만 조회한다.

- `AT_OR_ABOVE`: 목표 가격이 배치 최고가 이하이면 배치 안에서 목표 가격에 도달한 것으로 판정한다.
- `AT_OR_BELOW`: 목표 가격이 배치 최저가 이상이면 배치 안에서 목표 가격에 도달한 것으로 판정한다.

조회된 알림은 조건부 UPDATE로 `ACTIVE`일 때만 `FIRED`로 바꾼다. 변경 행 수가 1인 경우만 이번 처리의 결과 목록에 넣는다. 다른 Consumer 처리가 먼저 상태를 바꾸었거나 이미 처리된 알림이면 변경 행 수가 0이므로 결과에서 제외한다. 이 DB 상태 전이가 동일 알림의 반복 처리를 막는 기준이다.

**예상 상황과 현재 대응**

- 같은 이벤트가 다시 소비되거나 여러 이벤트가 같은 목표가를 만족: `FIRED` 상태와 조건부 UPDATE가 중복 상태 변경을 막는다.
- 이벤트 한 건에서 같은 종목 알림이 많음: DB가 일치하는 ACTIVE 알림을 반환하고 Consumer가 각 결과를 처리한다. 특정 가격대에 알림이 몰릴 때의 지연·DB 부하는 아직 측정되지 않았다.
- 처리 도중 DB 오류 또는 역직렬화 오류: 예외를 Consumer 메서드 밖으로 전달한다. 재시도 횟수, 재시도 간격, DLQ로의 이동은 현재 명시적으로 설정되어 있지 않으므로 운영상 복구 정책이 필요하다.
- 상태가 `FIRED`로 바뀐 뒤 프로세스가 중단: 현재 이 상태는 판정 완료 표시일 뿐 실제 사용자에게 발송됐다는 뜻이 아니다. 발송 기능을 추가할 때 발송 성공·실패 상태와 재시도 방법을 별도로 설계해야 한다.

## 5. 장애와 부하 상황을 가정한 대응 방향

아래 항목은 현재 구현 완료를 뜻하지 않는다. 현재 코드가 보장하지 않는 동작을 운영 전에 어떻게 결정해야 하는지 정리한 것이다.

| 가정 상황 | 현재 동작 | 운영 전 필요한 결정 또는 대응 |
|---|---|---|
| 증권사 WebSocket 단절 | 자동 복구하지 않음 | 연결 상태 감지, 재연결 간격·횟수, 재연결 뒤 전체 종목 재구독, 중복 연결 방지 |
| 연결은 살아 있지만 체결이 오지 않음 | 거래가 없거나 구독이 거절된 경우 구분이 어려울 수 있음 | 구독 승인 상태와 마지막 수신 시각을 종목별/시장별로 관측 |
| 배치 중 앱 종료 | 메모리 배치 유실 | 허용 가능한 유실 구간을 정하거나 집계 버퍼를 복구 가능한 저장소에 두는 방안 검토 |
| Kafka 브로커 또는 발행 오류 | 실패 로그만 기록, 배치 재발행 없음 | 재시도 가능 오류 분류, 재시도 한도, 실패 이벤트 보관, 운영자 알림 기준 정의 |
| 특정 종목 체결 폭증 | 건수 제한은 배치 크기를 자르지만 수신 callback과 잠금 경쟁은 남음 | 수신량·배치 마감량·발행 지연·락 대기시간 계측, 측정 결과에 따라 격리/분산 방안 선택 |
| Consumer 처리 지연 | Kafka에 쌓인 레코드가 늘어남 | Consumer lag, DB 조회 지연, 파티션별 처리량 관측 후 Consumer 수와 파티션 수 조정 |
| DB 일시 장애 | 조건 판별 예외가 발생할 수 있음 | Kafka 재처리 동작과 offset 기록 시점, 재시도/DLQ 기준을 함께 검증 |
| 목표 가격을 지나갔다가 되돌아옴 | min/max는 배치 내 도달 사실은 보존 | 최초 도달 시각이나 체결 순서가 필요한 제품 요구인지 확인. 필요하면 이벤트 모델 변경 |
| 동일 알림의 중복 발송 | 현 단계는 실제 발송 전이라 발송 문제는 없음 | 실제 발송을 추가할 때 상태 전이, 외부 채널 응답, 재시도 및 중복 방지 키 정의 |

## 6. 현재 관측 가능한 신호

- WebSocket 연결, 구독 승인·거절, 체결 파싱 오류 로그
- Kafka 발행 성공 시 토픽·파티션·offset, 발행 실패 시 오류 로그
- 목표 가격 조건 충족 로그의 알림 ID, 시장, 종목, 조건, 목표 가격, 체결 이벤트 ID
- Kafka UI에서 토픽별 파티션과 메시지 확인

아직 처리 지연, 초당 이벤트 수, Consumer lag, DB 조회 지연을 종합해 보는 메트릭 대시보드는 없다. 로그만으로 최대 처리량이나 SLA를 주장하지 않는다.

## 7. 설계 판단 요약

현재 시스템은 **수신량을 종목별 짧은 배치로 압축하고, Kafka에 분산 저장한 뒤, DB 조건 조회와 원자적인 상태 변경으로 한 번만 조건 충족 결과를 만드는 구조**다. 이로써 개별 체결을 모두 전달하는 비용과 동일 알림의 중복 상태 변경을 줄인다.

그 대가로 배치 시간만큼 판정이 늦고, 개별 체결 순서와 최초 도달 시각을 잃으며, WebSocket·Kafka·DB 장애 복구가 충분히 구현되지 않았다. 따라서 다음 단계에서는 무조건 복잡한 분산 구조를 먼저 추가하기보다, 수신량·배치 발행량·Kafka lag·DB 처리시간을 관측하고 위 장애 시나리오 중 제품이 허용할 유실과 지연을 결정해야 한다.
